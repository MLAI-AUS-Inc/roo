# Invoice source recovery: scoped pay-cycle reads

Status: approved for Native implementation on 12 October 2026. Production deployment remains a separate action. User-authorized browser verification found no MLAI workspace in the available account.

## Problem and intended result

An ordinary invoice should read the relevant Studio pay cycle, reuse already checked evidence, and generate every builder's scheduled invoice from one all-builder report. It should not reconstruct the workspace separately for each member.

The incident investigation observed 618 candidate issues, roughly 1,854 issue/history/version requests, and a first draft taking about 10.5 minutes. Eva's mapping was valid; Linear returned HTTP 400 with GraphQL `RATELIMITED` after the shared 2,500-request window was exhausted. The generic worker error discarded the reset deadline and retried after about 60 seconds. Existing `StudioSourceAPI` batches eight issues and persists evidence, but invoice CLI composition still selects `ReportAPI`. Merely switching readers would reduce calls while retaining the oversized search; this revision changes discovery too.

## Scope and time

The approved payable scope remains the five project IDs in `roo/timesheets.py:PROJECTS`: Master App, Cybertest, Project Ironman, Project Acquire, and Aaron AI. Studynash, Present Studio, and MLAI Studio operations remain excluded. A Studio name or issue prefix identifies where to search; it does not grant payment eligibility. Resolve and verify the Linear team IDs associated with the approved project IDs during private source preflight, paginate the project/team relations, and retain the verified IDs in the source namespace. If the projects span several teams, search that set. Never substitute the Slack workspace ID (`config.team`) for a Linear team ID. Team names are display information, not runtime authorization keys. If team membership cannot be verified, block generation with a scoped-source error.

Use the existing Melbourne fortnight selector and exact `(start, end]` cutoff reconstruction. On 12 October, the current draft is work after 9 October noon through the draft's capture time, for the 23 October noon payment cutoff; the latest closed fortnight ends 9 October noon. Do not reinterpret “last pay cycle” as a rolling 14 days or silently replace `current` with `latest`. Preserve first cutoff 11 September and source beginning 28 August noon. Full issue history, including events before the pay window, remains necessary to establish first completion and avoid paying reopened work twice.

## Discovery and evidence algorithm

Add an invoice/timesheet-specific `InvoiceSourceAPI(StudioSourceAPI)` in `roo/invoice_source.py`; keep the client-report reader's discovery contract intact. Reuse its eight-issue evidence batches, version checks, and complete-history fallback. The new reader maintains a private, versioned source index alongside existing evidence receipts, using atomic `ReceiptStore` files and locks; no database migration is needed.

A source generation contains the scope fingerprint, source beginning, last successful refresh-start watermark, relevant issue IDs and evidence digests, and checked outsider versions. Index scope includes organization, credential fingerprint, Slack workspace, verified Linear teams, approved projects, first cutoff/source beginning, timezone, rubric, and reader algorithm version. Evidence keeps its existing credential/organization isolation; index/report reuse additionally binds configuration and ledger inputs. Never persist credentials themselves.

1. **Initialize historical coverage once.** Add an explicit private `--prepare-source` operation for rollout preparation; it creates no invoice, allocation or Slack delivery. Until a compatible complete index exists, ordinary invoice collection returns `invoice_source_not_prepared` without launching a broad bootstrap inside a member request. Preparation discovers coverage from 28 August through the refresh time, retains full evidence for issues that are or were in an approved project, and publishes the index only after the entire pass succeeds. This includes an initial changed-issue reconciliation outside the current Studio projects to find work moved away after a historical cutoff. It is a one-time, resumable preparation cost, not a workspace-history scan for each invoice. Existing successfully checked evidence is reusable. A failed preparation produces a resumable waiting result, never a partial/zero invoice. Initialization writes source evidence only: drafts still simulate missing historical allocations in memory; final reports alone persist them chronologically through the existing ledger code.
2. **Read the requested period within Studio.** The primary lightweight query uses verified Linear team IDs AND approved project IDs AND `createdAt <= report_end`, with `(completedAt > period_start AND completedAt <= report_end) OR updatedAt >= refresh_lower_bound`. Include archived issues, all current states, and all assignees. Do not filter to the requesting member: cutoff ownership can differ from the current assignee. The initial lower bound is source beginning; subsequent lower bounds are the last successful watermark minus a five-minute overlap. Deduplicate pages/IDs and reject invalid or repeated cursors.
3. **Reconcile changes and retained IDs.** Perform a lightweight workspace `updatedAt >= refresh_lower_bound` query for IDs, current project/team, timestamps, and archival/deletion indicators. This safety probe is bounded by recent changes, not workspace age. Retain and directly reconcile every known relevant/deferred ID needed by unfinished periods even if it now sits outside Studio or disappears from the listing. Recognize already allocated IDs from the ledger and skip new accounting evidence for them, even if they appear in the delta; immutable sealed periods need no new source read. For previously unknown outsiders or previously checked outsiders whose version changed, read compact paginated project-transition history (`id`, `createdAt`, `fromProjectId`, `toProjectId`) and a post-read version check. Promote only issues whose project history intersects the allowlist to full accounting evidence; persist a versioned negative result for the others. This closes the unknown cross-team move gap without pretending a team-only query can discover it.
4. **Refresh selected full evidence.** Fetch full candidate fields in batches for every relevant ID needed for unfinished periods, including retained and deferred IDs, even when its issue version is unchanged; use the established complete candidate fingerprint and evidence digest before cache reuse. Keep complete history for selected issues, including first completion, state, owner, project and effort transitions. This detects label-name changes even when Linear leaves the issue timestamp unchanged. Deferred IDs are always reconsidered. Missing/inaccessible known evidence is a source-coverage failure, not a removed row or a cached resurrection. Complete archived work stays discoverable. Persist completed evidence batches incrementally but publish the new index/watermark only after all discovery and required evidence succeed. Capture the watermark at refresh start and do not impose an upper `updatedAt` bound: edits during pagination are seen now or in the next overlapping refresh. Never advance to the finish time and skip concurrent edits. A final report requires a closing discovery pass and required-ID fingerprint/version reconciliation: any changed candidate set or version requires another reconciliation before sealing. Allow at most three stability passes within the attempt budget; otherwise raise `linear_source_unstable` and do not seal. This is an observed stable collection, not a claim of a provider-wide transactional snapshot.
5. **Build from complete coverage.** Return retained historical evidence needed to replay missing periods plus current/deferred evidence to the unchanged accounting functions. An empty ledger does not justify starting at 9 October or forgetting September allocations. Once earlier periods are sealed, omit their allocated evidence from new-period work, while preserving their immutable saved report bytes. Saved finals and already saved request artifacts continue replaying without Linear reads.

For a first-seen outsider, examine all compact project history necessary to establish whether it was ever in scope; do not stop at the latest delta boundary and lose earlier project membership. For an already classified outsider, a tail-only check is allowed only after pagination ordering is verified and continuity to its previous checked version is proven. The schema exposes `last`/`before` but does not establish ordering direction by itself; use complete compact pagination until that behavior is verified.

The public [Linear SDK schema](https://raw.githubusercontent.com/linear/linear/master/packages/sdk/roo-standalone/schema.graphql), inspected on 12 October 2026, exposes date/team/project issue filters but no project-transition filter on `Issue.history`. Therefore an unknown changed outsider cannot safely be dismissed using its current project alone. After preparation, ten thousand unchanged unrelated issues should cause no history requests; a newly changed outsider can require a compact move-history check. Do not promise “zero outside-team requests” or claim completeness from current team membership alone. Hard-deleted never-observed issues cannot be reconstructed by this API; this pre-existing visibility limit remains explicit. Loss of access to a known relevant issue fails closed. No new webhook/backend system is proposed. Discovery/transport/access failures block report generation; existing individual effort/mapping/reconstruction exceptions remain reviewable deferred rows under existing accounting rules. Uncertainty about an outsider's historical project membership must block coverage rather than silently classify it as unrelated.

## Share the work, without stale draft reuse

Add `TimesheetService.report_batch()` as a context manager that memoizes complete all-builder reports within one captured worker batch only. Its cache key binds selector, exact captured `now`, preview mode, configuration/source namespace and the ledger fingerprint; return deep copies. Use it around invoice command processing and around scheduled invoice processing. Nineteen builders requesting the same report in that batch incur one discovery/refresh/build, followed by 19 private member projections. Independent later requests refresh changes; there is no cross-request freshness TTL or indefinitely cached draft. Failed or incomplete source generations are never memoized. A report carrying legitimate deferred accounting exceptions may retain the existing report semantics, but source-discovery failure must raise before a report exists.

Retain existing ownership checks for every member and delivery. If a slow draft crosses Friday noon, discard it and follow the existing final-period transition. Reuse must not bypass membership changes, correction/ledger updates, or immutable-final checks. Final persistence changes the ledger, so subsequent calls first use existing immutable reports rather than a stale memoized draft.

## Quota and recovery

Bind both evidence storage and a `linear-cooldowns` receipt before verification or collection can call Linear. In `StudioSourceAPI.linear`, lock one cooldown key per existing organization/credential/Slack-workspace namespace across deadline check, request, and rate-limit recording. Honor HTTP 429 and GraphQL `RATELIMITED` at HTTP 200 or 400. Persist the maximum validated deadline from stored cooldown, `Retry-After`, and exhausted quota reset headers through existing `retry_time`; keep its 60-second minimum. Contention raises `linear_source_busy` without HTTP. Corrupt/unreadable cooldown state raises `linear_cooldown_unavailable` without HTTP; a failed write retains the deadline in memory. Preserve sanitized errors and no provider body/credential logging.

All queued actors and scheduled builders sharing the private volume honor that deadline and resume completed batches after restart. No periodic 60-second provider hammering during a known hour-long reset. Saved artifact delivery/acknowledgement recovery remains available during source cooldown. The client-report deployment currently uses another volume: this protects workers sharing a volume, not every application using the Linear credential. Other consumers can still exhaust the upstream quota.

Private waiting notices replace the generic failure text only for `invoice_source_not_prepared`, provider quota, and local budget/stability waits. Use “Your invoice request is saved. Studio’s invoice source is being prepared; it will resume once ready.” for preparation; “Your invoice request is saved. Linear is busy. The earliest retry is {Melbourne date/time and timezone}; it will resume when the source is available.” for a provider deadline; and “Your invoice request is saved. Roo is still checking the source and will resume once ready.” for local budget/stability waits. These are earliest-retry/waiting statements, not completion ETAs. Persist the chosen reason, exact rendered text and original deadline in the existing once-per-request private notice receipt before delivery; later retries/restarts must reuse that content and never resend a confirmed or ambiguous notice. Keep PR 297’s public acknowledgement unchanged and disclose no invoice amounts, PDF contents or source details publicly.

## Cost and acceptance

Log aggregate counts for primary candidates, delta candidates, known-ID hydration calls, compact move-history checks, full evidence cache hits/misses, batches, pages, and refresh duration; do not log issue bodies or personal details. Compare cold bootstrap, normal cold period, unchanged refresh, one changed issue, and a 19-builder scheduled batch. For `N` new/changed relevant issues, existing full evidence costs approximately `2 × ceil(N / 8)` calls for single-page histories, plus candidate hydration and discovery; long histories and compact outsider checks add explicit counts. Bootstrap cost is reported separately. Bound each preparation/refresh attempt to 200 Linear requests and 45 seconds measured by a monotonic clock, checking before the next request; return a resumable `linear_source_budget` retry when exhausted, keeping completed receipts and leaving the published watermark unchanged. A single in-flight request may run to the existing HTTP timeout. Budget exhaustion also persists a namespace wait of at least 60 seconds (never shortening a provider deadline), so the next builder cannot immediately start another 200-call attempt. Use the same shared short wait for an unstable collection. These local limits are safeguards, not provider quota estimates. Nineteen invoices in one batch must not multiply source cost by 19. Target under one minute for a typical healthy post-bootstrap request, with an actual latency commitment only after authorized measurement; no guarantee based only on request counts.

Required offline acceptance covers real CLI GraphQL filters, 10,000 unchanged unrelated issues with no post-preparation history reads, unknown moved-out/cross-team tickets, archived/inaccessible evidence, long histories, empty-ledger bootstrap, pre-August completion then reopen, previous-period completion then reopen, deferred work, post-cutoff reassignment/effort edits, Friday noon/DST, membership isolation, corrections, quota/corrupt-state recovery, and duplicate/ambiguous delivery protections. A 19-member batch must produce the same per-member totals as the existing exhaustive reader on a synthetic mixed-history fixture.
