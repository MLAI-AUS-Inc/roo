# Hermes execution host operations

This package has offline protocol/policy tests. Its Docker images, Linux XFS
quota commands, Chromium login and noVNC handoff have **not** been executed on a
provisioned host. Keep the worker and browser flags disabled until the checks
below pass there. No host, cloud deployment or website account has been selected
or authenticated by this implementation.

## Host and storage boundary

Use a dedicated Linux VM for Public Roo execution. A container shares its host
kernel; Docker tool isolation is not a VM boundary. Put Admin Roo on a separate
host or security boundary with separate controller configuration and authority.
The controller remains outside task containers. Its Docker authority is
privileged host authority, even when the service runs as UID 10000. Restrict
operator access and the controller's inputs accordingly.

Provision a **separate, bounded XFS data filesystem** for `/var/lib/roo-hermes`,
mounted with project quota accounting and enforcement (`prjquota`). The supplied
example accepts at most 50 GiB total capacity and caps each task at 2 GiB and
50,000 inodes. These are initial capacity choices, not measured requirements.
No script here formats, mounts or resizes disks. Choose and provision the correct
volume through the host's reviewed infrastructure process. Do not put the task
root on the host root filesystem or substitute a bind mount of it.

Keep the filesystem mount and its parent directories root-owned. Create only
`/var/lib/roo-hermes/tasks` as UID:GID 10000:10000, mode 0700. Install the reviewed
quota helper outside the writable application checkout:

| Repository source | Installed path | Ownership/mode |
| --- | --- | --- |
| `hermes/storage/roo-hermes-quota` | `/usr/local/sbin/roo-hermes-quota` | root:root 0755 |
| `hermes/storage/quota.py` | `/usr/local/lib/roo-hermes-storage/quota.py` | root:root 0644 |
| `roo/hermes/storage.py` | `/usr/local/lib/roo-hermes-storage/storage_check.py` | root:root 0644 |
| `hermes/storage/quota.example.json` (review values) | `/etc/roo-hermes/quota.json` | root:root 0644 |

All installed parent directories must be root-owned and not writable by group
or others. Provision `/var/lib/roo-hermes-quota` root:root 0700 for the locked,
fsynced, never-reused project ID counter. Reserve the configured ID range on
this new dedicated filesystem. Do not reset the counter or reuse its range for
other software. Install the distribution's `xfsprogs` at the fixed
`/usr/sbin/xfs_quota` and `/usr/sbin/xfs_io` paths. The helper launches these with
a clean environment and does not accept executable/configuration paths.

The controller may invoke only the installed helper as root, using a reviewed
sudoers rule without `SETENV`. The program accepts exactly:

```text
sudo -n /usr/local/sbin/roo-hermes-quota check
sudo -n /usr/local/sbin/roo-hermes-quota prepare TASK_UUID-ATTEMPT_HEX
```

`check` is read-only. `prepare` accepts one canonical lowercase UUID plus the
fresh 32-character attempt suffix generated by the controller. It rejects paths,
extra arguments, symlinks and nonempty workspaces. It temporarily freezes the
namespace under root ownership, sets a new project's hard byte/inode limits,
assigns the task tree, then confirms the project ID, inheritance flag and quota
readbacks before restoring ownership. Configuration/state writing happens
**after** successful quota preparation. Any nonzero exit prevents agent launch.
The root task directory is briefly unavailable to new controller filesystem
operations; serialize preparation on this host. Existing container bind mounts
continue referring to their own directories.

A helper process/host crash during namespace freezing can leave a directory
root-owned. Fail closed: stop every affected container, inspect the counter and
XFS projects, then repair ownership explicitly. A stale counter `.new` file also
requires operator inspection, not automatic counter reset. Never report a quota
as enforced merely because `xfs_quota` exited zero: the helper reads back limits
and each directory's project/inheritance fields.

Monitor overall free bytes/inodes, number of retained attempts, image layers,
Docker logs and the controller's own logs. Project quotas bound task bind mounts;
they do not bound Docker's image/log storage. Keep retention short and use Docker
log rotation or the launcher's disabled task log driver. The controller must
remove task containers before collecting output or deleting their directories.

## Fixed backend and public web routes

`docker-compose.hermes-infrastructure.yml` creates two internal Docker networks:

- `roo-hermes-internal`: ordinary tasks and the fixed backend proxy.
- `roo-hermes-web`: only tasks with an explicit public-web grant, the same backend
  proxy, and the optional web egress service.

Only the proxies attach to an outbound network. No service publishes a host
port. Docker internal networking alone does not block access to host services
through the bridge gateway. Install the reviewed
[host input policy](network/roo-hermes-host.nft) through the host firewall manager
and verify it before enabling work. Compose assigns stable bridge interfaces
`br-roo-hermes` and `br-roo-web`; the policy drops host-bound traffic arriving
from either interface without flushing other firewall rules. Do not rename a
bridge without updating and rechecking this boundary.

Install `hermes/network/check.py` as
`/usr/local/lib/roo-hermes-network/check.py` (root:root 0644) and
`hermes/network/roo-hermes-network` as `/usr/local/sbin/roo-hermes-network`
(root:root 0755), with root-owned nonwritable parent directories. The controller
may sudo only `/usr/local/sbin/roo-hermes-network check`. This fixed read-only
helper uses `/usr/sbin/nft --json` with a 10-second deadline, checks both real
bridge interfaces, and requires the exact active IPv4/IPv6 INPUT chain and drop
rule. A dormant table, wrong hook/interface, extra conditions or an earlier
accept rule fails the check. It never installs or changes the firewall. Example
sudoers entries, restricted to the dedicated service account `roo-hermes`
(provisioned UID/GID 10000), are:

```sudoers
roo-hermes ALL=(root) NOPASSWD: /usr/local/sbin/roo-hermes-network check
roo-hermes ALL=(root) NOPASSWD: /usr/local/sbin/roo-hermes-quota check
roo-hermes ALL=(root) NOPASSWD: /usr/local/sbin/roo-hermes-quota prepare *
```

The quota helper itself strictly validates the full argument list/attempt name;
there is no path, command or environment override. Do not grant direct `nft`,
`xfs_quota`, shell or unrestricted sudo through this rule. Validate sudoers via
the host's normal `visudo` process. The worker's Docker group authority remains a
separate privileged trust boundary. The backend proxy can POST only the exact task MCP and model completion
paths, with the task token supplied by the worker. It forwards to one configured
HTTPS hostname, verifies its certificate and rejects upstream redirects. It has
no backend worker/admin/provider secret. The actual backend rechecks the task
grant and quota on every call; network routing alone does not authorize a tool.

The optional `public-web` profile requires `ROO_HERMES_WEB_HOSTS`, a list of exact
public DNS names. The CONNECT proxy accepts port 443 only, rejects IP literals,
private/special-use DNS answers and encrypted/mismatched TLS server names. It
connects to the already-validated literal IP, not a second DNS lookup. Every new
CONNECT, including one made after a redirect, is checked independently. The task
container stays on an internal network even if it removes all proxy environment
variables. Its fixed Chromium flags also disable ECH and QUIC for compatibility
with this gate. Direct HTTP/UDP/IPv6 internet access is unavailable.

This proxy does not decrypt TLS or inspect the encrypted HTTP Host/path. HTTP/2
connection coalescing or domain fronting can reuse a TLS connection with a
different HTTP authority, so it does not guarantee rejection of every cross-host
redirect. It enforces CONNECT destination and visible TLS SNI policy. Do not
allowlist open proxies, domain-fronting services or endpoints that tunnel to
arbitrary destinations. An allowed host remains an exfiltration destination for
information the task can read. Approve web access as part of task authority and
keep private tasks off that network unless their data policy permits it.
Chromium's `--no-sandbox` flag follows the pinned Hermes Docker launch behavior;
the containment boundary is the outer container and dedicated VM.

## Controller operation and recovery

The integrated worker is `python -m roo.proactive.worker` in the active
`roo-standalone` application. Provision its separate environment from
`.env.hermes.example`, with the dedicated backend worker key and derived image
digest. This code never loads Public Roo's or Admin Roo's dotenv files. A sample
host service is [systemd/roo-hermes-worker.service](systemd/roo-hermes-worker.service);
review its installation paths before use. It deliberately does not auto-restart
a failed controller. Keep the service unit, checkout and virtual environment
root-owned; only task directories belong to UID 10000. Store the service
EnvironmentFile as root:root 0600. Systemd reads it before dropping service UID.
Do not copy that file or its values into task mounts.

Run these modes as the configured host service identity with its dedicated
environment loaded by the service manager, not an interactive production dotenv:

```text
python -m roo.proactive.worker --check
python -m roo.proactive.worker --once
python -m roo.proactive.worker --reconcile
```

`--check` validates configuration, the derived image, internal networks, UID/GID,
private state directory and installed quota helper without claiming work or
contacting a model. It can create the controller lock file. `--once` claims at
most one eligible task and can call the configured development/staging services;
run it only when those external test actions are authorized. With flags disabled,
these commands report `disabled` rather than starting execution. A filesystem
lock permits one controller per task root; keep one controller/task root for this
host's shared internal networks and do not bypass it with extra worker instances.

For normal service operation, the controller claims backend work, creates and
quotas a fresh task container, supervises its grant heartbeat and deadline, stops
it, validates artifacts, then completes the backend task. It preserves an exact
host-only `completion-pending.json` receipt before sending completion. Neither
Hermes task mount includes that receipt. If the completion acknowledgement is
lost, it reports `completion_unknown`, retains the receipt and stops the
controller. Do not rerun the agent to guess whether completion happened.

Stop the service and run `--reconcile` through the same service environment. This
mode stops orphan task containers and replays only the fixed backend completion
request with the exact saved body; it does not execute Hermes. A successful
backend acknowledgement removes the receipt and discards the attempt directory.
Unresolved failures, including 409/403 responses, retain it for operator review.
Check the backend's committed task, owner and lease/grant status before deciding
what to do. Never edit a receipt to force acceptance, broadly retry side effects,
or delete it merely to make startup pass. Once all receipts reconcile, restart
the controller deliberately.

## Optional operator browser and authentication

Clean public-web tasks use the browser already included in the pinned Hermes
image through an explicit text/DOM toolset. Navigation and snapshots return
accessibility-tree text; no screenshots are automatically inserted. The model
proxy rejects image content, and the toolset omits `browser_vision`, image
analysis, browser vault, arbitrary CDP and generated browser execution tools.
This supports DOM-based research/navigation, not visual desktop reasoning or
canvas-only workflows. Ordinary terminal code can still create image files,
but those are not accepted as model input by the current proxy. The separate `docker-compose.hermes-browser.yml` is an **optional,
disabled deployment building block**, not an enabled authenticated-browser
integration. It must be wired into the controller/backend's lease lifecycle and
pass the host smoke tests before use. The current task worker does not attach
these CDP endpoints or start these sidecars automatically.

The sidecar provides Chromium, a virtual display, noVNC and an exclusive browser
transport gate. It has one authority/profile binding, a bounded 512 MiB ephemeral
profile, no host ports and no shared personal browser directory. It uses only
the restricted web network. Cookies disappear when the container stops. Durable
profile reuse is intentionally not configured: adding it requires a separately
encrypted, quota-enforced volume per authority, lifecycle/retention checks and
cookie revocation support.

Provide a controller-owned lease directory (read-only in the browser) containing
`lease.json`. Copy the disabled template, then have the controller atomically
replace it with these exact fields after authorization:

```json
{
  "version": 1,
  "authority_id": "one-authority",
  "profile_id": "one-profile",
  "attempt_id": "one-task-attempt",
  "mode": "operator",
  "expires_at": 0,
  "token": "replace-with-64-lowercase-hex-from-cryptographic-randomness"
}
```

The example's expiry/token are deliberately invalid. Real leases last at most
15 minutes and use `operator` or `agent` mode. Every mode/attempt/token change
invalidates existing sockets; expiry and malformed/missing state fail closed.
The gate checks active connections every 200 ms as well as on traffic. The
operator's TLS+HTTP Basic authentication is independent of this lease; merely
knowing the browser address cannot take over the session.

Provision a separate read-only operator authentication directory with `tls.crt`,
`tls.key` and `operators.htpasswd`. Supply an appropriate certificate and unique
operator password hash through the normal secret process, with files readable
only to the dedicated runtime identity. Neither password nor TLS private key
belongs in a task environment. There is no default password. Do not expose 8443
publicly: use authorized SSH/private-network access to the container address,
then open `/vnc.html` over TLS. Raw Chromium CDP, VNC and noVNC ports bind only to
loopback **inside** the sidecar.

Required controller workflow:

1. Bind a browser instance to the task's authorized owner and fresh attempt.
   Check the selected website account has only the approved authority.
2. To request login/takeover, cancel and confirm removal of the agent container,
   revoke its task capability, then issue a short operator lease. The browser
   gate closes the old CDP channel. An operator connects through protected access,
   signs in manually and completes MFA in this clean browser.
3. Returning control is an explicit authenticated operator action. Revalidate
   owner/grants/lease, issue a fresh task capability and agent browser token,
   then change to `agent` mode. The operator connection closes. Never resume an
   old expired ACP process or reuse a consumed approval.
4. Launch a fresh agent task with the exact browser WebSocket endpoint and token
   from this sidecar. The configured form is
   `ws://hermes-browser-PROFILE:9223/devtools/browser/BROWSER_ID?lease=TOKEN`.
   Obtain the browser ID by reading `http://127.0.0.1:9222/json/version` inside
   that exact sidecar through the trusted lifecycle service; validate the returned
   browser WebSocket path. Do not accept an endpoint from task input. Pinned Hermes accepts this
   full endpoint via `BROWSER_CDP_URL` or `browser.cdp_url`; it does not require
   public CDP discovery. Treat the whole URL as a secret and redact it in output.
5. On task cancellation, disconnect, expiry, owner change or completion, revoke
   both task and browser leases, kill/remove the task container and the browser
   sidecar, then discard its ephemeral profile. Mark expired login as needing
   sign-in; do not fall back to another user's profile.

A browser cookie is website authority outside the MCP broker. This gate controls
who operates that browser, not which actions the website permits. Prefer broker
APIs for service actions; approve an authenticated browser workflow separately.
The example does not claim passkey/security-key support or all MFA mechanisms.

## Required acceptance checks on the intended Linux host

Before enabling either worker flag, build and pin the derived image digest;
verify the offline ACP shim provenance/import check; parse the Compose profiles;
and run synthetic tasks with development-only credentials. Exercise:

- Ordinary Python/file output, MCP identity/resource restrictions and model caps.
- Deadline/cancel/lease-loss teardown, including a child ignoring SIGTERM, then
  confirm the named container and all child processes are gone.
- A task attempting excessive files/bytes reaches EDQUOT while host root and a
  different task remain usable; verify hard byte and inode limits separately.
- Direct internet, host gateway, metadata, private IP/DNS and nonallowed proxy
  destinations fail. Allowlisted HTTPS works, including Chromium subresources.
- Wrong/expired task tokens, prompt controls and unapproved dangerous commands
  fail safely; the review UI shows exact bounded command details when available.
- For optional operator browsing: no raw CDP/VNC access, wrong owner/profile/token
  rejected, agent sockets close before login, operator sockets close on resume,
  expiry/restart closes access, cancellation deletes both containers/profile.

Offline tests cover protocol, callbacks, redaction, artifact traversal, proxy
DNS/TLS policy, browser lease gating and quota command/readback logic. They do
not replace these container/kernel/browser end-to-end checks.
